# كتالوج فحوص أمن مستودعات GitHub

التاريخ: 27 أكتوبر 2026؛ اعتُمد الكتالوج كاملًا في 1 نوفمبر 2026. الحالة: نطاق معتمد ومراجع وثائقيًا؛ الفحوص الجديدة غير منفذة وغير مختبرة على GitHub.

يرتبط هذا الكتالوج بـ[نطاق المشروع](PROJECT_SCOPE.md). يستبدل قائمة الفحوص الستة بكتالوج معتمد من **20 فحص إعدادات و4 فحوص مشروطة بتوافر الخدمات الأمنية الأصلية**. يحافظ على معرفات الفحوص القديمة، ولا يغير نطاق مساهمة إصلاح القواعد والاستثناءات.

تحديث 1 نوفمبر 2026 وفق قرار المستخدم الأخير: **الفحوص الـ24 كلها ضمن نطاق GitHub المعتمد**. نبدأ بمحطة تسليم تشمل SC-01 وSC-02 وSC-03 وSC-10، إلى جانب دورة الاتصال والأدلة والمعالجة وإعادة التحقق ومحرك الإصلاح المحدود، ثم نستكمل البقية على دفعات. اعتماد الفحوص لا يعني تنفيذها أو التحقق الحي منها بعد؛ الفحوص الأمنية الأربعة معتمدة أيضًا ويتطلب تشغيلها توافر الخدمة والصلاحيات.

قيد النطاق المعتمد في 2 نوفمبر 2026: يطبق هذا الكتالوج في الإصدار الأول على مستودعات تملكها GitHub Organizations فقط. مستودعات الحسابات الشخصية خارج النطاق. لا يغير ذلك عدد الفحوص المعتمد، ولا يعني توافر بيانات كل فحص في كل مؤسسة.

## 1. لماذا هذه الزيادة؟

حماية الفرع تعالج مسار إدخال التغييرات، لكنها لا تغطي وحدها صلاحيات الأتمتة أو مشاركة الأسرار مع تشغيل غير موثوق أو مفاتيح النشر أو صلاحية أدلة الفحص. لذلك نضيف مجموعات تعالج أسئلة مختلفة، مع إعادة استخدام الجمع والتقييم والأدلة والمخالفات وإعادة التحقق.

معيار إدخال الفحص: خطر مفهوم للمستخدم، بيانات يمكن طلبها من API موثق، سؤال ضيق قابل للاختبار، وإجراء معالجة يمكن للمسؤول اتخاذه. وجود الفحص في أدوات أخرى لا يلغي قيمته التشغيلية؛ لكنه يمنع وصفه بأنه مساهمتنا الجديدة. التميز المستهدف يبقى تحليل التراكب والاستثناءات وتوليد إصلاح يحافظ على العمليات المعلنة ضمن النموذج المدعوم.

لا نفعّل كل الفحوص لكل مستودع. يحدد ملف متطلبات المؤسسة القيم والسياسات المناسبة؛ لا نعامل كل مستودع عام أو كل استثناء أو كل مفتاح كتابة على أنه مشكلة.

## 2. حماية الفرع والمراجعات والاستثناءات — 10 فحوص

النطاق الأول: الفرع الافتراضي الموجود. الحكم هنا على الإعدادات النشطة المقروءة؛ أثرها على الأطراف يعرض في تحليل منفصل. مصادر هذه المجموعة: [القواعد المتاحة](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets) و[Rulesets API](https://docs.github.com/en/rest/repos/rules).

| المعرف | الفحص وسؤال المؤسسة | الدليل المطلوب | الحد الذي يجب إظهاره |
|---|---|---|---|
| SC-01 | اشتراط PR قبل إدخال التغيير | قاعدة `pull_request` نشطة ومنطبقة | وجود القاعدة لا ينفي الاستثناءات منها |
| SC-02 | حد الموافقات المطلوب | عدد الموافقات المطلوب مقارنة بحد المؤسسة | لا يراجع تاريخ كل موافقة أو أهلية كل مراجع |
| SC-03 | تقييد الدفع القسري | قاعدة `non_fast_forward` نشطة | قد يستثنى منها طرف؛ لا نسميها منعًا شاملًا |
| SC-04 | تقييد حذف الفرع | قاعدة `deletion` نشطة | ليس ضمانًا ضد كل طريق لفقد البيانات |
| SC-05 | إلزام checks التي اختارتها المؤسسة | أسماء checks المطلوبة في القواعد | لا نختار الاسم لأنه يحتوي كلمة security ولا نحكم على جودة الفحص |
| SC-06 | اشتراط مصدر نتيجة check | ربط check بتطبيق GitHub المتوقع | لا يثبت سلامة التطبيق أو صدق كل نتيجة يصدرها |
| SC-07 | إبطال الموافقات القديمة عند تحديث PR | إعداد إسقاط المراجعات القديمة | يعالج اعتماد مراجعة سبقت تغييرات لاحقة؛ لا يعني إعادة فحص محتوى الشيفرة |
| SC-08 | موافقة مستقلة على آخر دفع قابل للمراجعة | إعداد الموافقة على آخر دفع | مختلف عن حد عدد المراجعات؛ نتحقق من الإعداد دون تحليل PRs تاريخية |
| SC-09 | اشتراط توقيع commits عندما تطلبه السياسة | قاعدة `required_signatures` | التوقيع لا يثبت أن الشيفرة آمنة؛ لا نفرض الشرط على كل فريق |
| SC-10 | الاستثناءات ضمن القائمة المعتمدة | هوية القاعدة والمصدر والطرف ونوعه و`bypass_mode` مقارنة بالسجل المعتمد | يكشف استثناءً غير معتمد؛ تحليل إمكان تجاوز الحماية فعليًا وظيفة المحرك المنفصلة |

**تفصيل SC-07 وSC-08:** الأول يراجع سياسة صلاحية الموافقات بعد التغيير؛ الثاني يراجع شرط استقلال الموافقة على آخر دفع. لا نعُدّ مجرد تغيير أسماء الحقول فحصين؛ السؤالان مختلفان، وقد تختار المؤسسة أحدهما أو كليهما.

نعتمد القواعد النشطة المنطبقة من `GET /repos/{owner}/{repo}/rules/branches/{branch}`، ونطلب تعريفات Rulesets عندما يلزم المصدر والاستثناءات. واجهة القواعد المنطبقة لا تغني عن جمع الاستثناءات. يتطلب ظهور `bypass_actors` في تفاصيل Ruleset صلاحية كتابة على القاعدة حسب الوثائق؛ غيابه ليس قائمة فارغة. لا ننفذ عمليات كتابة بسبب امتلاك الهوية صلاحية أوسع. [تفاصيل Ruleset](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset).

التوريث وClassic Branch Protection قد يؤثران في الحكم. نعرض مصدر الإعدادات، ولا نصدر حكمًا على الحماية الفعلية عندما تكون طبقة مؤثرة مجهولة أو غير ممثلة. لا نسطح القواعد والاستثناءات إلى قائمة واحدة تفقد ارتباط كل استثناء بقاعدته.

## 3. إعدادات GitHub Actions — 7 فحوص

النطاق: إعدادات Actions للمستودع والسياسات الأعلى المؤثرة والمتاحة. لا نفحص ملفات Workflow في هذه الدفعة. [إعدادات Actions الرسمية](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository).

| المعرف | الفحص وسؤال المؤسسة | الدليل المطلوب | الحد الذي يجب إظهاره |
|---|---|---|---|
| SC-11 | تقليل الصلاحية الافتراضية لـ`GITHUB_TOKEN` | `default_workflow_permissions` مقابل السياسة | ليست إثباتًا لصلاحيات كل Workflow أو Job؛ قد تحدد الملفات صلاحيات أخرى |
| SC-12 | تقييد موافقات Actions على PR | `can_approve_pull_request_reviews` | نقارنه بالحاجة الفعلية؛ لا ندعي أنه يمنع كل بوت خارجي من الموافقة |
| SC-13 | مصادر Actions ضمن السياسة المعتمدة | `allowed_actions` وإعدادات المصادر المختارة | مصدر مسموح أو ناشر موثّق لا يعني أن كل Action آمن |
| SC-14 | اشتراط تثبيت Actions إلى commit محدد | `sha_pinning_required` | فحص سياسة التثبيت، وليس مسح كل مرجع في YAML |
| SC-15 | عدم إرسال أسرار/متغيرات إلى تشغيل Fork خاص دون اعتماد | `send_secrets_and_variables` | يخص سياسة Forks الخاصة المعنية؛ لا يثبت عدم تسريب الأسرار بطرق أخرى |
| SC-16 | عدم إرسال رمز كتابة إلى تشغيل Fork خاص دون اعتماد | `send_write_tokens_to_workflows` | منفصل عن الأسرار؛ رمز كتابة قد يسمح بتعديل موارد حتى دون أسرار مخصصة |
| SC-17 | موافقة مناسبة قبل تشغيل مساهمات Fork | سياسة المساهمين الخارجيين أو `require_approval_for_fork_pr_workflows` بحسب النوع | لا نحكم بأن الموافقة البشرية تجعل الشيفرة الخارجية آمنة |

هذه الحقول ومسارات قراءتها موثقة في [Actions Permissions API](https://docs.github.com/en/rest/actions/permissions). القراءة على مستوى المستودع لهذه الإعدادات تتطلب عادة `Administration: read`؛ يجب التحقق من صلاحية كل endpoint المختار عند بناء الاتصال.

مسارات الجمع، كلها `GET` تحت `/repos/{owner}/{repo}`:

| المسار | يستخدم في |
|---|---|
| `/actions/permissions` | حالة Actions وسياسة المصادر والتثبيت |
| `/actions/permissions/selected-actions` | تفاصيل المصادر عند اختيار وضع selected |
| `/actions/permissions/workflow` | صلاحيات الرمز والموافقات |
| `/actions/permissions/fork-pr-contributor-approval` | سياسة موافقات المساهمين الخارجيين |
| `/actions/permissions/fork-pr-workflows-private-repos` | سياسة تشغيل Forks الخاصة والرموز والأسرار والموافقة |

ضوابط التفسير التي نعتمدها في التنفيذ:

- إذا كانت Actions معطلة ومسموحًا تعطيلها، لا نحسب الفحوص الفرعية نجاحات أمنية. نوثق عدم انطباقها. إذا كان تشغيل خدمة فحص محددة مطلوبًا، فتعطيلها قد يخالف ذلك المتطلب.
- في SC-13 نبدأ بمقارنة سياسة إعدادات معتمدة محددة؛ لا نبني محللًا عامًا لاحتواء جميع أنماط wildcard. الحالات التي لا نفهم دلالتها أو توريثها تبقى غير محسومة.
- لا نفسر إعداد مستودع أقل تقييدًا بمعزل عن قيد أعلى مفروض. نجمع الدليل المؤثر أو نضيق السؤال إلى الإعداد المرئي ونعرض القيد صراحة.
- GitHub يوضح أن شرط تثبيت Actions لا يعني تثبيت كل reusable workflow، وأن آلية lockfile المدعومة لها دلالات أخرى. لا نحول SC-14 إلى ادعاء «كل الاعتماديات ثابتة» ولا نعيد تنفيذ تحقق GitHub بالبحث النصي. [نطاق خيار التثبيت](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository).
- SC-15 وSC-16 يفحصان سياسة تشغيل Forks الخاصة عند انطباقها. لا يغطيان تلقائيًا كل event أو استخدام غير آمن لـWorkflow؛ فهذه الدفعة لا تحلل محتوى الملفات.

## 4. الوصول والتكاملات — 3 فحوص

| المعرف | الفحص وسؤال المؤسسة | الدليل المطلوب | الحد الذي يجب إظهاره |
|---|---|---|---|
| SC-18 | مفاتيح النشر ذات الكتابة معتمدة | جرد Deploy Keys، ومعرف المفتاح و`read_only` وحالته إن توفرت، وقائمة اعتماد المؤسسة | لا نحذف مفتاح كتابة صالحًا؛ نكشف الكتابة غير المعتمدة. لا نثبت أن المفتاح الخاص محفوظ بأمان |
| SC-19 | ظهور المستودع يطابق تصنيف المؤسسة | `visibility` مقابل تصنيف محفوظ | المستودع العام ليس مخالفة إذا كان عامًا عن قصد؛ لا نستنتج تصنيف البيانات من اسمه |
| SC-20 | النقل الآمن لـWebhooks النشطة | مخطط URL يساوي HTTPS والتحقق من TLS غير معطل | لا يثبت أمان الخادم المستقبل أو التحقق من توقيع الرسائل |

مصادر الجمع:

- `GET /repos/{owner}/{repo}/keys` يتطلب `Administration: read` ويعرض صفة القراءة فقط. لا نحتاج تخزين نص المفتاح في التقرير. [Deploy Keys API](https://docs.github.com/en/rest/deploy-keys/deploy-keys).
- `GET /repos/{owner}/{repo}` يوفر بيانات المستودع. تُقارن بقيمة متوقعة يحددها المسؤول؛ لا يكفي الجلب دون سياسة مرجعية. [Repositories API](https://docs.github.com/en/rest/repos/repos).
- `GET /repos/{owner}/{repo}/hooks` يتطلب `Webhooks: read`. القيمة `insecure_ssl=0` تستخدم التحقق من الشهادة. لا نتصل بعنوان Webhook ولا نختبر التسليم ولا نعدله. [Repository Webhooks API](https://docs.github.com/en/rest/repos/webhooks).

نحتفظ بأقل دليل لازم لفحص النقل: معرف Hook وحالته ومخطط النقل وإعداد TLS. نحجب سر Hook ومكونات URL الحساسة من السجلات والتقارير. قيمة سر مقنّعة في API لا تثبت وجود تحقق سليم لدى الطرف المستقبل. مراجعة الإعدادات لا تتطلب بناء مستقبل Webhooks لمنصتنا.

## 5. خدمات GitHub الأمنية — 4 فحوص مشروطة

هذه المجموعة توسع الاستفادة من أدلة موجودة؛ لا نبني SAST أوSCA أوكاشف أسرار جديدًا. تعتمد على توافر الميزة ونوع المستودع والخطة والصلاحيات.

| المعرف | الفحص وسؤال المؤسسة | الدليل المطلوب | الحد الذي يجب إظهاره |
|---|---|---|---|
| SC-21 | تفعيل Secret Scanning المطلوب | حالة `security_and_analysis.secret_scanning` عندما تكون متاحة | تفعيل الخدمة لا يثبت عدم وجود أسرار أو كشف كل أنواعها |
| SC-22 | تفعيل Push Protection المطلوب | حالة `secret_scanning_push_protection` | إعداد حماية الدفع لا يثبت غياب التجاوزات أو منع كل سر |
| SC-23 | تنبيهات Dependabot ضمن مهلة المعالجة | حالة التنبيهات وتمكين الخدمة وشدة التنبيه وتاريخ إنشائه مقابل مهلة المؤسسة | نحكم على التنبيهات المعلومة؛ لا نعلن سلامة جميع الاعتماديات |
| SC-24 | دليل Code Scanning حديث وخالٍ من خطأ معلن ضمن النطاق | أحدث تحليل مناسب لكل tool/category/ref مطلوب، ووقته و`error` و`warning` و`commit_sha` | الحداثة لا تثبت أن التحليل يغطي HEAD الحالي أو كل اللغات أو يكتشف كل ثغرة |

تمثيل الحالات والبيانات:

- بيانات `security_and_analysis` مقيدة بالصلاحيات. اختفاء الحقل لا يعني تعطيل الخدمة. لا نطلب قيم الأسرار المكتشفة لأداء SC-21 أوSC-22. [بيانات المستودع](https://docs.github.com/en/rest/repos/repos).
- يُقرأ تمكين تنبيهات الاعتماديات من `/repos/{owner}/{repo}/vulnerability-alerts`؛ نجاح القراءة الموثق يعيد `204` عند التمكين. لا نفسر `404` وحده على أنه تعطيل مؤكد دون إثبات الوصول والصلاحية. [واجهة التمكين](https://docs.github.com/en/rest/repos/repos#check-if-vulnerability-alerts-are-enabled-for-a-repository).
- تُقرأ التنبيهات من `/repos/{owner}/{repo}/dependabot/alerts` بصلاحية `Dependabot alerts: read`. نجمع الصفحات المطلوبة وحالات التنبيهات التي تشملها السياسة. الزمن المحسوب من إنشاء التنبيه هو **عمر التنبيه**، وليس تاريخ إدخال الثغرة إلى المشروع. [Dependabot Alerts API](https://docs.github.com/en/rest/dependabot/alerts).
- تُقرأ تحليلات الشيفرة من `/repos/{owner}/{repo}/code-scanning/analyses` بصلاحية `Code scanning alerts: read`. نفرق بين tool وcategory والفرع، ولا نختار أي نتيجة حديثة من مستودع أو لغة أخرى لإخفاء غياب النتيجة المطلوبة. نعرض التحذيرات ولا نعتبرها نجاحًا نظيفًا تلقائيًا. [Code Scanning API](https://docs.github.com/en/rest/code-scanning/code-scanning#list-code-scanning-analyses-for-a-repository).

في SC-23، وجود تنبيه من الشدة المطلوبة تجاوز المهلة هو مخالفة مثبتة بالنسبة لذلك التنبيه. غياب النتائج لا يكفي لنجاح الفحص قبل التحقق من تشغيل الخدمة واكتمال الجمع؛ وحتى عند النجاح يبقى الحكم على مخزون التنبيهات المتاح. إذا عطّل المسؤول خدمة تطلبها السياسة، نعرض مخالفة التغطية بدل «لا توجد ثغرات».

في SC-24، تحفظ السياسة الأدوات والفئات المطلوبة والحد الأقصى للعمر. غياب التحليل المطلوب بعد جمع كافٍ مخالفة دليل؛ أما تعذر قراءة التحليلات فحالة غير محسومة. إذا كان آخر تحليل فاشلًا، نظهره ولا نخفيه باختيار تحليل قديم ناجح. يسجل آخر نجاح معلوم منفصلًا. ووقت الرفع ليس بالضرورة وقت فحص أحدث شيفرة.

## 6. عقد النتيجة والأدلة

كل نتيجة ترتبط بسؤال محدد ونسخة السياسة ونطاق المستودع أوالفرع ونافذة الجمع وإصدار المقيّم ومصدر الدليل. تحفظ القيم اللازمة والتفسير، مع تقليل البيانات الحساسة. لا نعد بأن طلبات API المتعددة لقطة ذرية؛ نعرض زمن الجمع، ونكشف تغيرًا مؤثرًا إذا استطعنا، وإلا نصرح بقيد الاتساق.

ربط المخالفات المتكررة يتبع هوية محددة في [وثيقة النطاق](PROJECT_SCOPE.md): المؤسسة، ومعرف المستودع الثابت، ومعرف الفحص، ونوع النطاق وقيمته، وموضوع المخالفة عند تعدده. في SC-01 وSC-02 وSC-03 مخالفة لكل فحص وفرع مع أدلة الطبقات؛ وفي SC-10 يضاف مصدر Ruleset ومعرفه ونوع الطرف ومعرفه، دون دمج استثناءات مختلفة. يحفظ كل ظهور وأدلته ونسخة سياسته؛ تغير نتيجة أو وصف أو وضع تجاوز لا يمحو التاريخ، والجمع الجزئي لا يثبت زوال مخالفة.

نفصل بين:

| البعد | الحالات والمعنى |
|---|---|
| انطباق الفحص | منطبق، غير منطبق بسبب مثبت، أو تعذر تحديد الانطباق |
| نتيجة سؤال منطبق | مستوفى، غير مستوفى بدليل، أو غير محسوم |
| حالات انتهاء التشغيل | مكتمل، جزئي، فاشل، أو ملغى؛ لا تساوي وحدها الحكم الأمني، ولا يغلق الإلغاء مخالفة |
| دعم التنفيذ | مدعوم في النسخة الحالية، أو غير مدعوم؛ لا يختفي من التقرير إذا طلبه المستخدم |

أمثلة إلزامية:

- نقص صلاحية أو حقل، انقطاع pagination، أو rate limit قبل اكتمال الجمع: لا PASS اعتمادًا على غياب البيانات.
- دليل صريح على مخالفة يكفي لإثبات تلك المخالفة حتى إذا بقيت بقية البيانات ناقصة؛ التقرير يعلن الجزئية ولا يدعي اكتمال التقييم.
- عدم وجود Deploy Keys بعد جرد مكتمل يعني عدم وجود مفاتيح كتابة مخالفة في ذلك الجرد. لا يعني أن كل وصول إلى المستودع آمن.
- عدم انطباق سياسة Forks الخاصة على مستودع عام لا يولد نقطة نجاح؛ تُستخدم سياسة النوع المناسب عند طلبها.
- استثناء وافقت عليه المؤسسة لا يعد فشلًا في SC-10، لكنه قد يؤدي إلى إخفاق متطلب آخر في تحليل أثر الحماية.
- بيانات قديمة لا تستخدم لحكم حالي دون إظهار العمر وسياسة صلاحيتها.

## 7. كيف نقبل دعم كل مجموعة؟

هذه معايير تحقق مقترحة، وليست نتائج اختبارات منفذة:

| المجموعة | الحالات التي يجب إثباتها قبل وصفها بأنها مدعومة |
|---|---|
| الفروع والمراجعات | إعداد مستوفٍ وآخر مخالف، قاعدة غير نشطة أو غير منطبقة، طبقة موروثة، استثناء معلوم وآخر تعذرت قراءته |
| Actions | السياسة المطلوبة ومخالفتها، Actions معطلة، Fork عام وخاص، توريث مؤثر، حقل غائب، وحالات إعدادات المصادر المدعومة |
| المفاتيح والظهور وWebhooks | مفتاح كتابة معتمد وغير معتمد، جرد فارغ مكتمل وجرد جزئي، ظهور مقصود وآخر مخالف، HTTPS مع TLS صحيح ومعطل وHook غير نشط |
| الخدمات الأمنية | ميزة متاحة وأخرى متعذرة، قائمة فارغة مع تمكين مثبت وأخرى دون إثباته، تنبيه قبل المهلة وبعدها، تحليل قديم أو فاشل أو لفئة/فرع مختلف |

نختبر حساب الأحكام ببيانات مرجعية، ثم صحة جمعها ودلالاتها في مختبر GitHub مصرح به. لا نعد الاختبار ببيانات مصطنعة إثباتًا لتكامل حي. ولا ننشئ أسرارًا حقيقية أو نغير إعدادات مستودعات إنتاجية للاختبار. كل تغيير مختبري يتطلب نطاقًا مصرحًا به وهوية مناسبة.

لقبول المحطة الأولى نختبر الفحوص الأربعة باستخدام GitHub App نفسها، ونثبت عزل مؤسستين تجريبيتين داخل المنصة ببيانات وعضويات منفصلة. تجربة مستخدمين من فريق خارجي اختيارية وليست شرط تسليم؛ الاختبار المختبري لا يثبت توفير وقت فريق فعلي. تلزم معايير قبول كل مجموعة عند تسليم دفعتها، وتلزم للفحوص الـ24 عند قبول نطاق GitHub كاملًا؛ تعذر بيئة اختبار مناسبة يسجل عائقًا أمام التحقق ولا يحسب نجاحًا أو اكتمالًا.

## 8. أثر التوسعة على التصميم والتنفيذ

لا تحتاج التوسعة Microservices أو لغة جديدة. تضاف عمليات جمع محددة إلى تكامل GitHub، ومقيّم صغير لكل سؤال مستقل داخل وحدات التطبيق القائمة. تعاد الاستفادة من المهام المحفوظة والأدلة والنتائج والمخالفات والتقارير وإعادة التحقق.

أقل إضافات إلى النموذج المنطقي:

- معرف الفحص ومعلماته ونطاقه وانطباقه، ضمن كتالوج المتطلبات المقترح.
- دليل يصف مصدر البيانات وحقولها ونافذة جمعها واكتمالها، ضمن نموذج الأدلة نفسه.
- مراجع سياسة المؤسسة: checks والتطبيقات الموثوقة، والموافقات، والاستثناءات والمفاتيح المعتمدة، وتصنيف المستودع، ومهل التنبيهات وحداثة التحليلات.

لا نضيف 24 جدولًا أو 24 خدمة أو إطار Plugins عامًا من أجل 24 فحصًا. ولا نفترض أن كل سياسات المؤسسة تقبل محرك إصلاح آليًا. التوصية الإرشادية لإعداد Actions تختلف عن خطة إصلاح أثبت المحرك صلاحيتها داخل نموذجه.

يُطلب من الاتصال ما يلزم للفحوص المختارة فقط. لا نعطي كل مؤسسة كل صلاحيات GitHub لمجرد أن الكتالوج يحتوي فحوصًا إضافية. تظهر مصفوفة التغطية والبيانات غير المتاحة للمستخدم قبل تفسير التقرير.

## 9. ترتيب التسليم وحدود الالتزام

1. مسار كامل صغير: مؤسسة واتصال GitHub App مصرح به ونطاق ومهمة ودليل وفحص واحد ومخالفة وإعادة تحقق. يبدأ التحقق من فرضيات محرك الإصلاح مبكرًا ضمن الخطة.
2. استكمال محطة التسليم الأولى: SC-01 وSC-02 وSC-03 وSC-10، ودمج التحليل والإصلاح للحالات المدعومة. هذه الفحوص ترتبط مباشرة بالمساهمة وتستفيد من مصادر جمع متقاربة؛ فحص عدد الموافقات لا يعني دعم كل أعدادها في المحرك.
3. قبول دورة العمل والفحوص الأولى والمحرك وعزل المؤسستين ومعالجة الانقطاع وحد محاولات المهمة، ثم تحديث تقدير الجهد لبقية النطاق المعتمد.
4. تنفيذ SC-04 إلى SC-09 ثم Actions والوصول والتكاملات على دفعات معتمدة. يمكن تعديل ترتيب الفحوص بحسب جاهزية البيانات، مع بقاء جميعها ضمن النطاق.
5. تنفيذ التكاملات الأمنية الأربعة والتحقق منها في بيئة تتوافر فيها الخدمة والترخيص والصلاحيات. إذا تعذر أحدها، يسجل العائق ولا يُحسب منفذًا أو متحققًا منه دون دليل؛ إخراجه من النطاق يحتاج قرارًا صريحًا.

العدد 24 هو نطاق الفحوص المعتمد، والأربعة الأولى محطة تسليم ضمنه. نثبت تقدير الجهد بعد أول مسار حي كامل وقياس كلفة جمع البيانات واختبارها. لا توجد بيانات جهد تبرر الآن ضمان تنفيذ النطاق خلال شهرين أو الجزم باستحالته؛ ترتيب الدفعات لا يلغي الالتزام باستكماله ولا يحول البقية إلى إضافات اختيارية.

**النتيجة العملية المستهدفة عند استكمال التغطية:** يستطيع المسؤول العثور، مثلًا، على PR لا تُراجع تغييراته اللاحقة، أو سياسة Fork تمنح رمز كتابة غير مطلوب، أو مفتاح نشر غير معتمد، أو دليل فحص قديم؛ ثم يراجع السبب والدليل ويعالج الحالة ويعيد التحقق. هذه أمثلة من النطاق المعتمد، تسلم بحسب دفعات التنفيذ.

## 10. ما الذي تحقق في هذه المراجعة؟

راجعت الوثائق الرسمية المرتبطة أعلاه لتحديد مصادر البيانات وحدود الأسئلة. لم أجر اتصالًا حيًا بهذه الواجهات على مستودعات المستخدم، ولم أنفذ الفحوص أو أختبر صلاحياتها عمليًا أو أغير إعدادات GitHub. لم يتغير عرض السمينار أو نموذج Python. تعديل هذه الوثائق يثبت تصميم النطاق، لا تنفيذ المنصة.
