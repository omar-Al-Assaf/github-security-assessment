# سياسة Kanban ومراجع العمل

1 نوفمبر 2026. أنشأ المستخدم [لوحة GitHub Projects](https://github.com/users/omar-Al-Assaf/projects/1) المرتبطة بعمل المشروع، وأضاف إليها [AC-01، المهمة رقم 2](https://github.com/omar-Al-Assaf/github-security-audit/issues/2). اللوحة هي مرجع حالات المهام اليومية. يحفظ هذا الملف قواعد العمل والاعتمادات ومراجع البنود؛ لا ينشئ سجل حالة موازيا للوحة.

## حالات اللوحة

| الحالة | معناها |
|---|---|
| Backlog | عمل مطلوب لم تتوافر له بعد شروط السحب |
| Ready | مخرج واضح ومدخلات متاحة وشروط إنجاز محددة |
| In Progress | بدأ العمل الفعلي على البند |
| In Review | ينتظر مراجعة المخرج واعتماده |
| Done | استوفيت شروط الإنجاز والمراجعة وسجل دليلها |

## قواعد العمل

- وحدة العمل Issue لها مخرج واضح وشرط إنجاز ومرجع للدليل، مثل مصفوفة الصلاحيات أو مسار التهيئة. يربط PR بها عند وجود تغييرات ملفات؛ لا يعد PR المرتبط عملا مستقلا مكررا في حساب WIP.
- يبدأ البند عند سحبه من Ready إلى In Progress. ينتهي بعد استيفاء شرط إنجازه ومراجعته وتسجيل الدليل؛ إرسال مسودة للمراجعة ليس انتهاء.
- **الحد الإجمالي WIP = 1**، ويشمل In Progress وIn Review والتصحيح والتعثر بعد البدء. لا يقتصر على عمود التنفيذ.
- لا يسحب بند جديد عندما يشغل بند غير منته هذا الحد. يعالج سبب الانتظار أو يصغر البند قبل زيادة العمل.
- لا يوصف بند بأنه Ready ما دامت مدخلاته اللازمة غير متاحة. الانتظار قبل البدء يختلف عن التعثر بعده؛ الثاني يبقى ضمن WIP.
- قبول مراجعة توثيق لا يعني تنفيذ المنصة. وفي البنود التي يشترط إنجازها دمج PR، لا يكفي فتحه أو إغلاقه دون دمج. إغلاق PR دون دمج لا يحسب إنجازا تلقائيا.
- تسجل أوقات البدء والانتهاء والانتقالات من العمل الفعلي. لا تستنتج أوقات بدء تاريخية من تاريخ إنشاء Issue أو Commit.
- المرحلة الحالية للتصميم والتوثيق والفهم؛ لا يبدأ كود بناء المنصة قبل طلب المستخدم الانتقال إلى التنفيذ.

## اعتماد AC-01

اعتمد صاحب المشروع في 1 نوفمبر 2026 [مصفوفة الصلاحيات](ACCESS_CONTROL_MATRIX.md): المسؤول للإدارة والتشغيل والاطلاع، والمقيّم للتقييم والتخطيط ومتابعة المعالجة، والمراجع للاطلاع والتقارير. يشمل الاعتماد حدود المؤسسة وسحب الوصول وحماية آخر مسؤول.

مرجع الإغلاق: [المهمة رقم 2](https://github.com/omar-Al-Assaf/github-security-audit/issues/2) و[طلب المراجعة رقم 1](https://github.com/omar-Al-Assaf/github-security-audit/pull/1). شرط إنجاز هذه المهمة هو اعتماد التصميم وتوثيق القرار ومواءمة المراجع؛ لا يتطلب اعتماد بقية الحزمة أو دمجها، ولا يعني تنفيذ الصلاحيات أو اختبارها حيا.

هذه مراجع للمخرجات والاعتمادات السابقة، وليست حالات يومية بديلة عن اللوحة. لم تنشأ Issues لبقية البنود ضمن توثيق اعتماد AC-01.

| AUTH-01 — الدخول وتهيئة المؤسسة والمسؤول الأول والاسترداد | مسار واضح، وتحديد موضع كلمة المرور والتهشير وحماية الجلسة | AC-01 |
| ARCH-01 — المكونات وعقود التواصل | Component Diagram يستند إلى الصلاحيات والتهيئة وحدود Web وWorker | AUTH-01 |
| DATA-01 — نموذج البيانات وERD | المؤسسات والعضويات والمهام والأدلة والنتائج وتاريخها وعلاقاتها | ARCH-01 |
| FLOW-01 — تسلسل أول تقييم وحالات المهمة | Sequence وState للمسار الأول، بما فيه الانقطاع والإلغاء والإقرار النهائي | DATA-01 |
| GH-01 — عقد الوصول إلى GitHub App للمحطة الأولى | الصلاحيات وendpoints وتصميم التحقق المصرح به | نطاق المحطة الأولى؛ التنفيذ الحي يحتاج بدء مرحلة التنفيذ |
| DESIGN-01 — مراجعة الحزمة السابقة | [تقرير مراجعة المحتوى](DESIGN_CONTENT_REVIEW_2026-11-01.md) | إنجاز كتابة المراجعة لا يعني قبول الحزمة أو دمجها |

الفحوص الـ24 باقية ضمن نطاق GitHub، وAWS يأتي بعد إكماله إذا بقي وقت. يعتمد سحب أي بند جديد على حد WIP واستعداد مدخلاته.

## ما ينقص المتابعة

يلزم متابعة WIP والعدد المنجز وعمر البنود غير المنتهية وزمن إنجاز البند. لم تسجل أوقات العمل السابق بما يكفي لحساب هذه المقاييس؛ لا نستنتجها من تواريخ Commits.

لم نحدد بعد توقعا زمنيا للخدمة SLE مع احتماله. يثبت كتوقع أولي معلن ثم يراجع بالبيانات، ولا يقدم بوصفه قياس أداء سابقا أو وعد تسليم.

إنشاء GitHub Projects وحده لا يكمل المنهجية. يلزم تطبيق الحالات والشروط والتسجيل ومراجعة البنود المنتظرة بانتظام. تبقى الجاهزية وقبول المحتوى قرارا بشريا. عند متابعة اعتماد AC-01، تأكد إغلاق المهمة رقم 2 وظهور بطاقتها في Done بقراءة اللوحة بعد الإغلاق، دون الحاجة إلى نقلها يدويا. لم تراجع جميع إعدادات الأتمتة؛ لا يعمم هذا على كل مسار أو على إغلاق PR دون دمج.
