# نطاق المشروع وقراراته التقنية

التاريخ: 27 أكتوبر 2026.

المشروع: **منصة لتقييم الضوابط الأمنية وإدارة الأدلة في مستودعات GitHub**.

هذه الوثيقة تثبت اختيار التقنية وأولوية النواة اللذين اعتمدهما المستخدم، وتعرض نطاق إصدار أول مفصلًا مقترحًا للمراجعة. لا تعني وجود تنفيذ، ولا اعتماد المستخدم لكل تفصيل جديد أدناه. المنصة مستمرة بعد تخرج 1؛ نطاق الإصدار الأول يحدد ما نسلمه أولًا.

تحديث 27 أكتوبر: بناءً على طلب المستخدم زيادة قيمة الفحوص، توسع الكتالوج المقترح من 6 إلى 20 فحصًا أساسيًا و4 تكاملات أمنية مشروطة بالتوافر. أضيفت إعدادات Actions ومفاتيح النشر وظهور المستودع ونقل Webhooks وبيانات خدمات GitHub الأمنية. هذه زيادة موضحة في نطاق الجمع والتقييم، وليست توسعة تلقائية لمحرك الإصلاح أو ادعاء تنفيذ هذه الفحوص. تفاصيلها المرجعية في [كتالوج الفحوص](CHECK_CATALOG.md).

تحديث 1 نوفمبر 2026 بعد اجتياز السمينار بحسب إفادة المستخدم: اعتُمد الالتزام بـKanban والتطوير التكراري والتزايدي، وإكمال نطاق GitHub أولًا. يُنفذ تكامل AWS لاحقًا إذا بقي وقت بعد إنجاز النطاق الأول والتحقق منه. دعم AWS هدف لتكامل فعلي ضمن نطاق يُحدد قبل تنفيذه؛ لم تُعتمد بعد خدماته أو فحوصه أو إصلاح سياسات IAM. بدأ توثيق التصميم بـ[مخطط سياق النظام CTX-01](diagrams/context/01-system-context.md) بناءً على طلب المستخدم؛ المخطط يصف التصميم المستهدف ولا يثبت تنفيذ المنصة.

تثبيت نطاق التسليم في 1 نوفمبر 2026 وفق قرار المستخدم الأخير: **الفحوص الـ24 كلها ضمن نطاق GitHub المعتمد**. الفحوص SC-01 وSC-02 وSC-03 وSC-10 محطة تسليم أولى مع دورة الأدلة والمعالجة ومحرك الإصلاح المحدود، وليست بديلًا عن استكمال بقية الفحوص. تظل ضوابط محاولات المهمة وهوية المخالفة وقبول مؤسستين تجريبيتين دون اشتراط فريق خارجي معتمدة. اعتماد النطاق لا يعني تنفيذه أو ضمان إنجازه خلال شهرين؛ SC-21 إلى SC-24 معتمدة أيضًا، ويعتمد تشغيلها على توافر خدماتها وصلاحياتها.

## 1. القرارات المعتمدة وحالة العمل

اعتمد المستخدم في هذه المحادثة:

- ASP.NET Core 10 LTS مع C# للـBackend.
- Entity Framework Core مع Npgsql وPostgreSQL.
- Razor Pages مع HTML/CSS وBootstrap وJavaScript عند الحاجة للواجهة.
- تطبيق Modular Monolith، ومحرك التقييم والتخطيط المستهدف بلغة C#، وعامل خلفي يستخدم منطق المشروع نفسه.
- أولوية خدمات الفحص والأدلة والمعالجة على الجماليات والوظائف الثانوية.
- اعتبار المنصة أساسًا يستمر تطويره، لا نموذجًا يُتخلّص منه بعد تخرج 1.
- إدارة التنفيذ باستخدام Kanban والتطوير التكراري والتزايدي، مع أولوية إكمال GitHub قبل التوسع إلى AWS، وتقييد توسع AWS بالوقت المتبقي.

أنشأ المستخدم [لوحة GitHub Projects](https://github.com/users/omar-Al-Assaf/projects/1) للمتابعة اليومية، وتوثق [سياسة Kanban ومراجع العمل](KANBAN.md) قواعدها وحد العمل الجاري WIP = 1، بما فيه انتظار المراجعة. تسجيل التدفق ومقاييسه لم يكتمل بعد. اعتُمدت [مصفوفة الصلاحيات](ACCESS_CONTROL_MATRIX.md) في AC-01 بتاريخ 1 نوفمبر 2026؛ تفصل حدود الأدوار وسحب الوصول، وتشمل صلاحيات المسؤول التشغيل والاطلاع داخل مؤسسته. مكتبة الطوابير ومزود الاستضافة لم يُختارا بعد. لم تُنشأ مشاريع .NET أو قاعدة بيانات أو تكامل إنتاجي في هذه المهمة.

الموجود في مساحة العمل: نموذج Python بحثي محلي ووثائق وتجربة مقارنة محدودة وعرض سمينار. نحافظ على تجربة Python كمرجع؛ ننقل المنطق المطلوب إلى C# ونتحقق من النتائج قبل دمجه. لا نجعل Python تبعية تشغيلية للمنصة لمجرد وجود التجربة.

هذه الوثيقة تتقدم على ترشيح Django التاريخي في `research/architecture-stack-review-2026-10-27.md`. ملفا السمينار 05 الحاليان ما زالا يعرضان التقنية السابقة؛ لم يُعدّلا في هذه المهمة ويحتاجان مواءمة لاحقة.

## 2. تعريف النواة

تقرأ المنصة إعدادات حماية مستودعات GitHub وإعدادات تشغيل Actions والتكاملات المختارة ضمن نطاق مصرح به، وتقارنها بمتطلبات محددة للمؤسسة، وتحفظ الأدلة التي استندت إليها. وعند توافر الخدمات الأمنية الأصلية، تستفيد من نتائجها وبيانات تغطيتها. تعرض المخالفات وحدود الحكم، وتحلل أثر القواعد والاستثناءات للحالات المدعومة، وتقترح خطة إصلاح محدودة تحافظ على العمليات المعلنة، ثم تعيد التحقق بعد تطبيق المسؤول للتغيير.

الأولوية ليست عدد الفحوص، بل أن يكون لكل فحص سؤال محدد وبيانات كافية وحكم مفسر ودليل يمكن مراجعته. واجهة واضحة وRTL صحيح وسهولة قراءة النتائج متطلبات استخدام أساسية؛ الحركات والرسومات التزيينية ولوحات المؤشرات المعقدة مؤجلة.

## 3. حدود الإصدار الأول المقترحة

| البعد | الحد المقترح |
|---|---|
| الخدمة الخارجية | GitHub.com؛ لا GitLab أو Bitbucket أو GitHub Enterprise Server في الإصدار الأول |
| العميل المستهدف | مسؤول مستودعات أو مقيّم أمني ضمن مؤسسة أو فريق تطوير |
| المستودعات | مستودعات يختارها المسؤول وتسمح بها هوية الاتصال؛ لا اكتشاف مفتوح لمستودعات الآخرين |
| الفروع | فحوص الفروع وبيانات Code Scanning تستهدف الفرع الافتراضي أولًا؛ إعدادات المستودع وActions والمفاتيح وWebhooks لها نطاق المستودع |
| مصدر الإعدادات | Rulesets النشطة ومصادرها وطبقاتها؛ وواجهات إعدادات Actions والمستودع ومفاتيح النشر وWebhooks وفق الفحوص المفعلة |
| البيانات | إعدادات وبيانات وصفية وعضويات لازمة للحكم؛ لا تنزيل الشيفرة وتاريخها. بيانات Dependabot وتحليلات Code Scanning تكاملات مشروطة منفصلة |
| تنفيذ التقييم | طلب يدوي ينشئ مهمة خلفية محفوظة؛ الجدولة الدورية الواسعة لاحقًا |
| المعالجة | تتبع داخلي وخطة قابلة للمراجعة؛ يطبق المسؤول التغيير على GitHub يدويًا |
| الأدلة | ناتجة عن الجمع الفعلي مع زمنه ومصدره واكتماله؛ لا نستبدلها بملف تجريبي ونصفها بأنها أدلة حية |
| الواجهة | صفحات عملية للمستودعات والتقييمات والنتائج والأدلة والخطط، مع ملخص بسيط |

توافر Rulesets للمستودعات الخاصة والموروثة يعتمد أيضًا على خطة GitHub وصلاحيات الاتصال، وليس على شيفرة منصتنا وحدها. لا نعد بدعم كل أنواع الحسابات قبل التحقق. [GitHub Rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

**التعامل مع Classic Branch Protection:** نحاول كشف وجوده وقراءة بياناته المتاحة، لكن التحليل الكامل لتداخله وإصلاحه خارج نموذج التخطيط الأول. إذا كانت طبقة منه أو أي قيد آخر قد يغيّر العملية ولم نستطع تمثيله، نعلن الحالة غير مدعومة أو غير محسومة. لا نتجاهله ونصدر حكمًا شاملًا؛ GitHub يطبق القواعد التقليدية وRulesets معًا. [طبقات الحماية في GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#about-rule-layering).

## 4. خدمات النواة ومخرجاتها

| الخدمة | ما يدخل إليها | ما تقدمه للمستخدم |
|---|---|---|
| تحديد نطاق التقييم | المؤسسة والمستودعات والفرع والمتطلبات | نطاق محفوظ وقابل لإعادة الاستخدام، مع بيان قابلية الوصول |
| جمع بيانات الفحص | النطاق واعتماد الاتصال والفحوص المفعلة | أدلة الإعدادات ونتائج الخدمات المدعومة ومصادرها وصفحات الجمع والأخطاء |
| تقييم الإعدادات | الأدلة ونسخة متطلبات المؤسسة | نتيجة لكل سؤال مدعوم: مستوفى، غير مستوفى، أو غير محسوم مع السبب |
| تحليل أثر التراكب والاستثناءات | القواعد والأطراف والعضويات والعمليات المحددة | مصفوفة السماح والمنع وتفسير القواعد المؤثرة، داخل النموذج المدعوم |
| توليد خطة إصلاح | التحليل وقائمة السماح والمنع والتعديلات المسموحة | خطة وتفسير وأثر متوقع، أو سبب عدم إنتاجها |
| إدارة المخالفات وإعادة التحقق | النتائج وتعليقات المعالجة والتغيير الخارجي | متابعة المسؤول والحالة، ثم تقييم جديد ومقارنة موثقة |
| عرض الأدلة وإصدار التقرير | التقييمات والأدلة والخطط | تقرير بسيط قابل للمراجعة يوضح النطاق والنتائج والمصادر والقيود |

«خدمة» هنا وظيفة يقدمها المنتج؛ لا تعني Microservice مستقلة.

تفكيك الخدمات إلى سلوكيات المنصة موثق في [حصر المتطلبات الوظيفية](FUNCTIONAL_REQUIREMENTS_INVENTORY.md): 7 خدمات للنواة تضم 22 متطلبًا رئيسيًا، ومع 6 متطلبات مساندة يصبح المجموع 28 متطلبًا رئيسيًا. الفحوص الـ24 تفاصيل متفرعة من متطلب تنفيذ الفحوص، وليست 24 خدمة إضافية.

## 5. كتالوج الفحوص الموسع

المرجع المفصل للأسئلة والحدود ومصادر البيانات هو [CHECK_CATALOG.md](CHECK_CATALOG.md). يحتفظ بمعرفات الفحوص الستة السابقة، ويضيف فحوصًا لمخاطر أخرى:

| المجموعة | المعرفات | العدد | ما تغطيه |
|---|---|---:|---|
| حماية الفروع والمراجعات والاستثناءات | SC-01 إلى SC-10 | 10 | PR والموافقات ومنع التحديث القسري والحذف والفحوص المطلوبة ومصدرها والمراجعات القديمة وآخر دفع والتوقيع والاستثناءات المعتمدة |
| إعدادات GitHub Actions | SC-11 إلى SC-17 | 7 | صلاحيات الرمز وموافقة البوتات ومصادر Actions وتثبيت إصداراتها وسياسات Forks |
| وصول المستودع والتكاملات | SC-18 إلى SC-20 | 3 | مفاتيح النشر ذات الكتابة وظهور المستودع ونقل Webhooks |
| خدمات أمنية أصلية عند توافرها | SC-21 إلى SC-24 | 4 | تفعيل كشف الأسرار وحماية الدفع وتنبيهات Dependabot وحداثة أدلة Code Scanning |

حجم الكتالوج المعتمد: **20 فحص إعدادات + 4 فحوص خدمات أمنية مشروطة بالتوافر**. الفحوص الـ24 ضمن نطاق التنفيذ المتفق عليه، لكن ذلك لا يعني انطباقها جميعًا على كل مستودع أو توافر صلاحياتها. عدد الفحوص لا يساوي عدد المتطلبات الوظيفية أو عدد ضوابط NIST المغطاة.

**محطة التسليم الأولى:** SC-01 لاشتراط PR، وSC-02 لحد الموافقات، وSC-03 لمنع الدفع القسري، وSC-10 لاعتماد الاستثناءات. اختيرت لأنها ترتبط مباشرة بقواعد الحماية ومساهمة المحرك وتستفيد من مصادر جمع متقاربة. تنفذ SC-04 إلى SC-09 وSC-11 إلى SC-20 في دفعات تالية معتمدة، وكذلك SC-21 إلى SC-24 مع توفير متطلبات الخدمات. مراجعة الجهد تضبط ترتيب الدفعات والتقدير الزمني، ولا تسقط فحوصًا من النطاق تلقائيًا.

محطة التسليم الأولى ليست أربعة فحوص منفصلة فقط: تشمل الاتصال الفعلي، والعضويات والصلاحيات، والمهمة المحفوظة، والدليل والنتيجة، ومتابعة المخالفة وإعادة التحقق، وخطة الإصلاح للحالات المدعومة أو سبب عدم إنتاجها. قراءة عدد الموافقات في SC-02 لا توسع تلقائيًا نموذج PR المحدود في محرك الإصلاح. يراجع تقدير المدة بعد أول مسار حي كامل؛ لا توجد بيانات جهد تثبت الآن أن النطاق المعتمد ينجز خلال شهرين أو يستحيل إنجازه خلالهما.

**فصل ضروري:** وجود إعداد منع الدفع القسري لا يثبت منع طرف مستثنى منه. وتحديد فحص CI مطلوب لا يثبت فعاليته في اكتشاف ثغرات. نعرض نتيجة الإعداد وأثر الاستثناء ومعطيات خدمة الفحص الخارجية كلًّا بمعناه. لا نعتبر اسم Check يحتوي كلمة security دليلًا على جودته.

الزيادة تحقق تغطية عملية أوسع، لكنها ليست بذاتها مساهمة بحثية جديدة. لا يتوسع محرك الإصلاح آليًا ليولد خططًا لكل هذه الفحوص؛ نطاقه في القسم التالي.

## 6. نطاق المساهمة أضيق من قائمة الفحوص

نثبت في أول نسخة من محرك الإصلاح نطاقًا يمكن اختباره:

- عمليات تحديث مباشر طبيعي، وتحديث Non-fast-forward، وPR في الحالة المبسطة المدعومة.
- قواعد اشتراط PR ومنع Non-fast-forward، مع always bypass وأطراف وعضويات معلومة.
- حدود التجربة الحالية تشمل PR بموافقة مؤهلة واحدة؛ إضافة الحالات الأوسع تحتاج توسيع النموذج والتحقق منه.
- طبقات متعددة، منها طبقات ثابتة لا يسمح المحرك بتعديلها.
- قائمة صريحة بما يجب السماح به وما يجب منعه لكل طرف.
- تعديلات مسموحة وكلفة معلنة وحد للبحث وعدد المرشحين والوقت.

يمكن فحص إعداد حذف الفرع أو required checks في الخدمة العامة دون الادعاء أن المحرك يولد إصلاحًا لهذه الخصائص. وجود قيد إضافي يؤثر في سيناريو التخطيط يستلزم تمثيله أو رفض التخطيط لذلك السيناريو؛ لا نسقط القيد من المدخلات لمجرد أن محركنا لا يعرفه. الافتراضات المختبرية بأن الشروط الأخرى مستوفاة لا تتحول إلى ضمان لمنظومة إنتاجية.

مخرجات المحرك: خطة، لا تغيير مطلوب، بيانات ناقصة، حالة غير مدعومة، متطلبات متناقضة، انتهاء ميزانية البحث، أو عدم العثور على خطة داخل مجال اكتمل بحثه. لا نحول آخر حالتين إلى استحالة مطلقة. وتبقى أمثلية الكلفة مقيدة بالمجال المفحوص.

الخطة مرتبطة بنسخة دليل ونسخة متطلبات. نتائجها توقعات نموذجية ضمن النطاق، وليست إثباتًا بأن GitHub نفذها. الاختبار السلوكي الحي، عندما يجري، يكون في مختبر مصرح به منفصل عن فحوص مستخدمي المنصة.

## 7. ما يجب أن يصاحب كل نتيجة

- السؤال أو المتطلب، ونطاق المستودع والفرع والأطراف إن كان السؤال خاصًا بأطراف.
- النتيجة وتفسير مفهوم، والقيم المطلوبة والقيم المقروءة.
- أساس النتيجة: قراءة إعدادات أو استنتاج نموذج محدد؛ لا نوحي بحدوث اختبار حي لم يُنفّذ.
- مصدر الدليل ونافذة جمعه واكتمال الصفحات والبيانات اللازمة.
- نسخة المتطلب والمقيّم والمحرك عند استخدامه.
- روابط الدليل المحفوظ والقيود أو البيانات الناقصة.

غياب `bypass_actors` لا يعني قائمة فارغة. توثيق GitHub يربط إظهار هذا الحقل بصلاحية كتابة هوية الطلب على القاعدة. نختبر أقل صلاحيات لازمة، مع بقاء التطبيق دون تطبيق تلقائي للإصلاح. [GitHub Get a repository ruleset](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset).

فشل التشغيل منفصل عن نتيجة المتطلب. إعادة التحقق تنتج تقييمًا وأدلة جديدين؛ إغلاق المخالفة إداريًا لا يغير النتيجة الأمنية السابقة. لا نعرض درجة أمان إجمالية تخفي الفحوص غير المحسومة أو غير المدعومة.

نحفظ الانطباق منفصلًا عن الحكم: فحص لا ينطبق بسبب موثق لا يُحسب PASS. أما نقص الصلاحية أو غياب حقل أو صفحة أو تعذر تحديد دعم الميزة فيؤدي إلى عدم الحسم. تعطيل ميزة تتطلبها سياسة المؤسسة مخالفة، وليس سببًا آليًا لوصف الفحص بأنه غير منطبق. قائمة تنبيهات فارغة لا تثبت سلامة الشيفرة أو تشغيل الخدمة.

**هوية المخالفة المتكررة:** داخل النطاق الأول نستخدم المؤسسة في المنصة + معرف مستودع GitHub الثابت + معرف الفحص + نوع النطاق وقيمته + موضوع المخالفة عند تعدده. نطاق الفرع هو مرجعه الكامل مثل `refs/heads/main`، ونطاق المستودع قيمة صريحة مختلفة؛ لا نعتمد اسم المستودع أو وصف المخالفة النصي مفتاحًا للهوية. لا يدخل وقت الفحص أو حكمه أو حالة المعالجة في الهوية.

- في SC-01 وSC-02 وSC-03 توجد مخالفة مجمعة لكل فحص وفرع، وترتبط بها أدلة الطبقات المؤثرة. تعديل Ruleset لا ينشئ تلقائيًا مخالفة جديدة للسؤال نفسه.
- في SC-10 يضاف مصدر Ruleset ومعرفه ونوع الطرف ومعرفه إلى الموضوع؛ فلا ندمج استثناءين لطرفين مختلفين أو مجموعتي قواعد مختلفتين. يحفظ وضع التجاوز كقيمة مرصودة؛ تغيره لا يمحو تاريخ الاستثناء نفسه.
- كل ظهور جديد يرتبط بتقييمه ودليله ونسخة السياسة والمقيّم، ويضاف إلى التاريخ دون استبدال السابق. عودة المخالفة بعد زوالها تعيد فتح السجل نفسه. تغير السياسة يوضح كتغير متطلبات، ولا يوصف وحده بإصلاح الإعداد؛ وإذا تغير معنى الفحص نفسه فتلزم هوية دلالية جديدة أو ترحيل صريح.
- نقص البيانات أو عدم ظهور العنصر في جمع جزئي لا يغلق المخالفة. يثبت زوالها بتقييم كافٍ للسؤال نفسه، أو توثق إزالة النطاق أو تغير السياسة كسبب مستقل. تحدد هوية موضوع أي فحص إضافي عند إدخاله؛ لا نبني الآن نظام دمج عامًا لنتائج أدوات أخرى.

## 8. وظائف مساندة لا نستغني عنها

- المؤسسات والمستخدمون وعضوياتهم، مع دور ثابت لكل عضوية: مسؤول أو مقيّم أو مراجع، وصلاحيات محددة على البيانات. ليس للمستخدم دور عام يورثه تلقائيًا إلى كل المؤسسات.
- حفظ اتصال GitHub وحمايته دون كشف أسراره في الواجهة أو الأدلة والسجلات.
- كتالوج صغير للمتطلبات ومعلماتها، دون منشئ سياسات عام في البداية.
- مهام تقييم وتخطيط محفوظة، وأخطاء مفهومة وإعادة محاولة محدودة وعدم تكرار النتائج النهائية.
- سجل لإجراءات المستخدمين والتقييمات والخطط، وسجل أخطاء تشغيل منفصل.
- مقارنة قبل المعالجة وبعدها، وتقرير أساسي قابل للطباعة، وتنبيه داخل التطبيق بحالة المهمة.
- Migrations واختبارات للسلوك الحرج وإجراءات نسخ احتياطي واسترجاع قبل الاستخدام الفعلي.

هذه الوظائف تحمي صحة الفحص وإمكان مراجعته. لا نؤجل العزل والتحقق من الصلاحيات أو اكتمال البيانات تحت عنوان تقليل الجماليات.

**حد محاولات المهمة:** الحد الابتدائي 3 محاولات إجمالًا للمهمة الواحدة، أي المحاولة الأولى وإعادتان كحد أقصى، وليس ثلاث إعادات بعد الأولى. هذا اختيار تشغيلي أولي يراجع عند القياس، لا رقم مستنتج من اختبار أداء. يسجل بدء المحاولة وعددها بصورة دائمة قبل العمل؛ انهيار Worker أو إعادة تشغيله لا يصفر العداد، والمحاولة التي بدأت ثم انقطعت تستهلك واحدة من الحد.

تعاد المحاولة تلقائيًا للأخطاء العابرة فقط، بعد تأخير محدود وضمن مهلة المهمة. نقص الصلاحيات أو المدخلات غير الصالحة يحتاج معالجة سببه، ونتائج المحرك مثل عدم الدعم أو تعارض الأهداف أو انتهاء ميزانية البحث لا تعاد تلقائيًا كأنها أخطاء اتصال. عند استنفاد الحد تصبح المهمة متعثرة نهائيًا مع سجل أسبابها؛ يمكن للمستخدم المخول طلب مهمة جديدة مرتبطة بعد معالجة السبب، دون محو المحاولات القديمة.

حد إعادة طلب HTTP مستقل عن حد محاولة المهمة، ويضبط داخل مهلة التنفيذ نفسها حتى لا تتضاعف الإعادات بلا حد. استرجاع مهمة منقطعة لا يسمح لمحاولتين بإقرار نتيجة نهائية واحدة مرتين؛ يثبت ذلك باختبار الانقطاع والاسترجاع. تبقى حدود وقت البحث وعدد مرشحيه والإلغاء مطلوبة داخل المحرك نفسه، فلا يعوض عنها عداد المحاولات.

فصل اتصال GitHub في UC02 يلغي المهام غير النهائية المرتبطة به ويمنع القراءات الجديدة عند نقاط التحقق. تسجل حالة «ملغى» منفصلة عن اكتمال التقييم وفشله؛ لا تعد إثباتًا لزوال مخالفة ولا تغير نتيجة انتهت بالفعل. يظل إيقاف طلب شبكة قائم مقيدًا بدعم الإلغاء ومهلته. وتعثر التنبيه بعد إقرار نتيجة نهائية لا يعيد تنفيذ المهمة.

## 10. ترتيب التنفيذ حول النواة

1. **تحقق الوصول والدلالات:** في مختبر مصرح به وباستخدام GitHub App المختارة، نتحقق من جمع القواعد والطبقات والاستثناءات والعضويات أو كشف نقصها صراحة. نجاح طلب بتوكن شخصي لا يكفي لقبول تكامل التطبيق.
2. **أول مسار كامل:** مستخدم ومؤسسة ومستودع وفرع افتراضي ومتطلب واحد، ومهمة خلفية ودليل ونتيجة ومخالفة محفوظة؛ ثم معالجة يدوية وإعادة تحقق بتاريخها.
3. **المحطة الأولى والمساهمة:** استكمال SC-01 وSC-02 وSC-03 وSC-10 ونقل محرك الخطط إلى C# مبكرًا. تقارن الحالات المرجعية القديمة كلها ثم حالات مستقلة وحدود البحث، دون انتظار استكمال الكتالوج.
4. **قبول المحطة الأولى:** تحقق مختبري من الدلالات المدعومة، وعزل مؤسستين، وحد المحاولات والانقطاع والاسترجاع، وتقرير يعلن الحدود والنتائج السلبية.
5. **استكمال النطاق المعتمد:** تضاف بقية فحوص الفروع ثم Actions والوصول والتكاملات والخدمات الأمنية الأصلية على دفعات، مع توفير متطلبات تشغيلها. كل دفعة لها معايير قبول؛ قبول الأربعة الأولى لا يعني اكتمال نطاق GitHub ذي الفحوص الـ24.

أبحاث المحرك واختبار دلالات GitHub تبدأ مبكرًا، حتى لو جاء دمجه في الواجهة لاحقًا. لا نؤجل اكتشاف خطأ في الفرضية الأساسية إلى نهاية المشروع.

يُدار هذا الترتيب عبر Kanban؛ البنود أعلاه ترتيب أولوية لتسليم زيادات قابلة للتحقق، وليست مراحل مغلقة تلزم إنهاء كل التحليل قبل أي تنفيذ. «إكمال GitHub» يعني إكمال وظائف النطاق المعتمد بما فيها الفحوص الـ24 والتحقق من تكاملها، ولا يعني دعم كل خدمات GitHub وفروعه وأنماط قواعده. تبقى الفحوص المشروطة مرتبطة بتوافر الخدمة والصلاحيات، وتُعلن حالات عدم التوافر أو عدم الحسم. تعذر بيئة اختبار فحص يسجل عائقًا أمام التحقق منه، ولا يحسب اكتمالًا أو يحذفه من النطاق؛ أي تقليص لاحق يحتاج قرار نطاق صريحًا.

بعد قبول نطاق GitHub، يُراجع الوقت المتبقي قبل سحب عمل AWS إلى التنفيذ. لا تكفي إضافة شاشة AWS لاعتبار التكامل منجزًا؛ يلزم اتصال فعلي مصرح به، وجمع بيانات للنطاق المتفق عليه، وتقييم أو استيراد نتائج بحسب الوظيفة المعتمدة، وأدلة محفوظة، وإعادة تحقق. أسلوب Modular Monolith يسمح بإضافة وحدة تكامل AWS، لكن تفاصيل الحسابات والموارد والفحوص والاعتماد ونموذج البيانات تحتاج تصميمًا خاصًا. لا ننشئ الآن محركًا عامًا للمزودين، ولا نفترض أن محرك إصلاح GitHub يصلح لتقييم سياسات AWS IAM أو إصلاحها.

## 11. معيار قبول النواة

معيار قبول محطة التسليم الأولى: يستطيع المستخدم تشغيل الفحوص الأربعة المحددة على نطاق مصرح به، والحصول على نتيجة صحيحة بالنسبة لسؤالها ومسنودة بدليل قابل للاسترجاع، ومتابعة مخالفة وإعادة التحقق منها دون فقد التاريخ، والحصول على خطة إصلاح للحالات المدعومة أو سبب واضح لعدم توليدها. قبول نطاق GitHub كاملًا يتطلب استكمال تنفيذ الفحوص الـ24 والتحقق منها بحسب شروطها؛ عدم توافر خدمة في مستودع مستخدم لا يعد نجاحًا للفحص، ويجب إثبات دلالاته في بيئة اختبار تتوافر فيها الخدمة.

**التجربة الأولى اللازمة:** مؤسستان تجريبيتان داخل المنصة، ببيانات وعضويات ونطاقات GitHub مختبرية مصرح بها. نثبت أن مستخدمًا غير مخول في المؤسسة الثانية لا يقرأ أو يعدل نطاقها أو مهامها أو أدلتها أو مخالفاتها أو خططها، حتى عند معرفة المعرفات. لا يلزم أن تكونا شركتين خارجيتين أو أن يشارك فريق حقيقي. تستخدم التجربة اتصال GitHub App نفسه، ولا يستعاض عن الاختبار الحي بملفات مصطنعة وحدها.

**تجربة فريق خارجي اختيارية:** تنفذ إذا توفر الوقت والمشاركون لقياس سهولة الاستخدام والفائدة العملية. غيابها لا يمنع قبول الاختبارات التقنية السابقة، لكنه يمنع الادعاء بأن المنصة وفرت وقت فريق حقيقي أو حسنت أداءه. الاختبار بمؤسستين لا يثبت وحده قابلية التوسع إلى أعداد كبيرة.

قبول كل فحص يتطلب إثبات حالة مستوفاة وحالة مخالفة وحالة بيانات ناقصة عند انطباقها. اختبار نموذج الحساب وحده لا يثبت صحة Collector أو عزل المؤسسات أو سلوك GitHub. اختبار المنع في المختبر يجب أن يترافق مع حالة مسموحة تنجح حتى لا يفسر اعتماد اتصال معطل على أنه نجاح لضابط الحماية.

يضيف الكتالوج حالات الانطباق والتوريث والبيانات القديمة بحسب كل مجموعة. الفحص لا يُوصف بأنه مدعوم حيًا قبل التحقق من جمع بياناته ودلالاته في بيئة مصرح بها. تحديث هذا النطاق استند إلى الوثائق الرسمية، ولم يتضمن تشغيل الفحوص الجديدة على GitHub.

أُنجز تفكيك أولي إلى 28 متطلبًا وظيفيًا رئيسيًا في [حصر المتطلبات](FUNCTIONAL_REQUIREMENTS_INVENTORY.md)، مع حدود قبول أولية. هذا ليس SRS نهائية أو وصفًا لما نُفّذ. إذا استُبدل متطلب تنفيذ الفحوص بمتطلب مستقل لكل واحد من الفحوص الـ24، يصبح العدد 51 بندًا بهذا المستوى من التفصيل، لا 52. العدد التقريبي السابق 25–30 متطلبًا ليس هدفًا نضيف وظائف لبلوغه؛ معيار النطاق هو اكتمال دورة التقييم والأدلة والمعالجة والمساهمة.
