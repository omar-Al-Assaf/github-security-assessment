# UC07 — طلب خطة إصلاح

الحالة: تصميم مستهدف. التاريخ: 1 نوفمبر 2026.

| العنصر | الوصف |
|---|---|
| الهدف | اقتراح تعديل لقواعد الحماية يحقق أهداف السماح والمنع المعلنة، ضمن حدود المحرك والتعديلات المسموحة |
| الطرف الرئيسي | المقيّم المخول داخل المؤسسة |
| المحفز | اختيار «طلب خطة إصلاح» من تقييم محفوظ |
| المدخلات | مرجع التقييم وأدلته، ونسخة أهداف المؤسسة، والأطراف والعضويات اللازمة، والطبقات القابلة للتعديل والثابتة، والتعديلات وميزانية البحث المسموحة |
| الشروط السابقة | جلسة وعضوية وصلاحية تخطيط صالحة، وتقييم محفوظ تابع للمؤسسة. اكتمال مدخلات التخطيط ودعمها يتحققان أثناء معالجة الطلب |
| المخرج | خطة وتفسير أثرها وكلفتها، أو نتيجة مفسرة لعدم إنتاج خطة، مرتبطة بنسخ المدخلات |
| ضمان الفشل | يبقى التقييم السابق محفوظًا، ولا يعدل الطلب إعدادات GitHub أو يصدر حكمًا قطعيًا من مدخلات غير كافية |

## المسار الأساسي

1. يختار المقيّم تقييمًا محفوظًا وأهداف السماح والمنع المعتمدة للمؤسسة، ضمن صلاحياته. ضبط الأهداف واعتمادها وظيفة الإدارة؛ طلب الخطة لا يمنحه صلاحية تغييرها.
2. تتحقق المنصة من التفويض وملكية التقييم والأهداف وحدود المؤسسة وصحة مراجع الطلب.
3. تحفظ مهمة تخطيط مستقلة قبل تأكيد قبولها، مرتبطة بالتقييم ونسخ الأدلة والأهداف وحدود التعديل والبحث، وتعيد مرجعها للمستخدم.
4. يقرأ Worker المدخلات المثبتة. يتحقق من اكتمال البيانات المؤثرة في العمليات المطلوبة، ودعم القواعد والاستثناءات، وعدم تناقض أهداف السماح والمنع.
5. يحسب المحرك الوضع الحالي. إذا كان يحقق جميع الأهداف، يعيد «لا تغيير مطلوب» دون إنشاء تعديل.
6. عند الحاجة إلى إصلاح، يبحث بين التعديلات المسموحة داخل حدود الكتابات والمرشحين والوقت، مع إبقاء الطبقات الثابتة دون تعديل. يرفض كل مرشح يخالف هدفًا معلنًا.
7. يختار خطة مقبولة وفق الكلفة المعلنة: عدد الكتابات أولًا، ثم مجموعات القواعد الجديدة، ثم تغييرات القواعد وعناصر الاستثناء. يتحقق من ترتيب تطبيق يحافظ على العمليات المعلنة المستوفاة أصلًا خلال الخطوات، ضمن النموذج المدعوم.
8. تحفظ المنصة الخطة وسببها وكلفتها وترتيب تطبيقها ومصفوفة القرارات قبلها وبعدها، ومراجع المدخلات وحدود الاستنتاج. يعرض أيضًا أي أثر معلوم على عمليات غير مدرجة في الأهداف، دون ادعاء حصر كل أثر خارجي.
9. يراجع المقيّم النتيجة. تطبيق المسؤول للتعديل على GitHub يدوي وخارج UC07، ثم يطلب إعادة التحقق في UC08.

## البدائل ونتائج المحرك

| الحالة | النتيجة والسلوك |
|---|---|
| طلب غير مخول أو مراجع لا تخص المؤسسة | رفض الطلب دون كشف بيانات أو إنشاء خطة |
| تعذر حفظ المهمة قبل قبولها | توضيح تعذر تسجيل الطلب؛ لا عرض له باعتباره مقبولًا |
| بيانات مؤثرة ناقصة | نتيجة «بيانات ناقصة» تحدد المطلوب استكماله؛ لا تفترض عضويات أو استثناءات فارغة |
| قواعد أو عمليات أو أوضاع تجاوز غير مدعومة | نتيجة «غير مدعوم» مع السبب؛ لا تسقط الطبقة المؤثرة من الحساب |
| أهداف متناقضة | نتيجة «متطلبات متناقضة» مع بيان التعارض القابل للإثبات |
| الأهداف مستوفاة في الحالة الحالية | نتيجة «لا تغيير مطلوب» مرتبطة بمدخلاتها، دون تغيير GitHub |
| انتهاء الوقت أو ميزانية المرشحين قبل اكتمال البحث المطلوب | إعلان «انتهاء ميزانية البحث» وحدود ما فُحص؛ لا ادعاء أمثلية لم تُثبت |
| اكتمال البحث داخل المجال دون خطة | إعلان «لا خطة ضمن المجال المفحوص»؛ لا استنتاج استحالة الحل خارج حدوده |
| خطأ تشغيلي عابر أو انقطاع Worker أو تعثر الحفظ | تطبق دورة المهام المحفوظة: حتى 3 محاولات إجمالًا بعداد دائم وضمن المهلة، دون تكرار النتيجة النهائية. تتوقف الإعادة الآلية عند استنفاد الحد |
| تغير معلوم في الإعدادات أو المدخلات بعد التقييم | تظهر محدودية صلاحية الخطة المستندة إلى النسخة القديمة والحاجة إلى تقييم جديد قبل اعتماد أثرها على الوضع الحالي |

## قواعد التفسير

- نتيجة المحرك، مثل عدم الدعم أو التناقض أو انتهاء ميزانية البحث، منفصلة عن فشل تشغيل المهمة؛ لا تعاد تلقائيًا كخطأ اتصال.
- التقييم الجزئي لا يمنع التخطيط آليًا إذا كانت جميع البيانات المؤثرة في السيناريو المطلوب كاملة ومدعومة. وجود قيد مؤثر مجهول يمنع الحكم القطعي.
- الخطة تحقق الأهداف المدخلة ضمن النموذج؛ لا تثبت صحة جميع عمليات المؤسسة أو نجاح التنفيذ على GitHub.
- الأفضلية مقيدة بمجال البحث الذي جرى التحقق منه، والكلفة مقياس للتعديلات وليست مالًا أو وقت تنفيذ مقاسًا.
- تنفيذ فحوص الكتالوج الـ24 لا يعني أن المحرك يصلح جميع أنواع مخالفاتها. النطاق الأول لقواعد PR ومنع Non-fast-forward والتجاوز والعمليات المدعومة كما تحدده وثيقة النطاق.
